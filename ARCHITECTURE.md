# وثيقة المعمارية البرمجية (ARCHITECTURE.md)
## الهيكل المعماري والنمط البرمجي لنظام إدارة مكتب المحاماة

### 1. النمط المتبع: Clean Architecture + Feature-First
تم تصميم النظام وفق أحدث معايير Clean Architecture مع تنظيم مجلدات الميزات (Feature-First) لفصل مسؤوليات العمل، وضمان قابلية الفحص البرمجي (Testability)، واستقلالية منطق العمل (Domain) عن واجهات المستخدم (UI) ومكتبات الطرف الثالث.

```text
lib/
├── core/                         # البنية التحتية المشتركة (Shared Infrastructure)
│   ├── database/                 # تعريف جداول Drift، قاعدة البيانات، والتحويلات
│   ├── security/                 # الأمان، التحقق الحيوي، تشفير البيانات، ومخزن الأسرار
│   ├── storage/                  # الوصول إلى التخزين (SAF) والتعامل مع الملفات
│   ├── backup/                   # محرك النسخ الاحتياطي المضغوط والمشفر، وGoogle Drive
│   ├── ai/                       # تكامل Google Gemini وموجهات الصياغة القانونية
│   ├── speech/                   # الإملاء الصوتي باللغة العربية
│   ├── notifications/            # نظام الإشعارات والتذكيرات المجدولة
│   ├── theme/                    # السمات اللونية والتحكم في أحجام الخطوط
│   ├── localization/             # التوطين والنصوص العربية
│   ├── routing/                  # تكوين GoRouter وحماية المسارات
│   └── utils/                    # أدوات التنسيق، التواريخ الهجرية والميلادية، والأرقام
│
├── shared/                       # المكونات والويدجت المشتركة عبر التطبيق
│   ├── widgets/                  # الأزرار، الحقول، البطاقات، وحوارات التأكيد
│   ├── models/                   # نماذج عامة
│   └── extensions/               # توسيعات Dart المفيدة (السياق، التواريخ، النصوص)
│
└── features/                     # حزم الميزات المستقلة
    ├── dashboard/                # لوحة التحكم والمؤشرات
    ├── clients/                  # إدارة الموكلين
    ├── cases/                    # إدارة القضايا والخصوم
    ├── file_manager/             # مستكشف الملفات وربط المجلدات SAF
    ├── hearings/                 # جلسات المحاكمة
    ├── tasks/                    # المهام والمهل
    ├── calendar/                 # التقويم الموحد
    ├── finance/                  # الأتعاب والمصاريف والدفعات
    ├── contracts/                # العقود والوكالات
    ├── contacts/                 # دليل جهات الاتصال والمحاكم
    ├── communications/           # سجل الاتصالات والاجتماعات
    ├── legal_library/            # المكتبة القانونية السورية
    ├── legal_ai/                 # المساعد الذكي
    ├── reports/                  # التقارير المالية والإحصائية
    ├── archive/                  # أرشفة القضايا
    ├── backup/                   # مركز النسخ والاستعادة
    └── settings/                 # إعدادات النظام والمظهر والأمان
```

### 2. بنية كل ميزة (Feature Folder Structure)
تحتوي كل ميزة على ثلاث طبقات نقية:
```text
feature_name/
├── data/
│   ├── datasources/             # التفاعل المباشر مع قاعدة بيانات Drift أو الملفات
│   ├── models/                  # نماذج البيانات والمحولات (Mappers)
│   └── repositories/            # تطبيق واجهات المستودعات (Repository Implementations)
│
├── domain/
│   ├── entities/                # كائنات الأعمال النقية (Pure Business Entities)
│   ├── repositories/            # عقود وواجهات المستودعات (Repository Contracts)
│   └── usecases/                # حالات الاستخدام وقواعد التحقق ومنطق العمل
│
└── presentation/
    ├── providers/               # مزودات Riverpod لإدارة الحالة
    ├── screens/                 # شاشات العرض الكاملة
    └── widgets/                 # ويدجت خاصة بالميزة
```

---

### 3. تدفق البيانات وإدارة الحالة (Data Flow & State Management)
1. **Presentation Layer:** ترسل الأحداث من واجهات المستخدم عبر استدعاء دوال مزودات الحالة (`StateNotifier` أو `Notifier` في Riverpod).
2. **Domain Layer:** يستدعي المزود حالة الاستخدام (`UseCase`) التي تطبق قواعد الأعمال القانونية والتحقق.
3. **Data Layer:** تنفذ حالة الاستخدام العملية عبر المستودع (`Repository`) الذي يتعامل مع جداول Drift ومحرك التخزين في بيئة آمنة غير تزامنية (`Future` / `Stream`).
4. **Reactive UI:** تستجيب الواجهات تلقائياً لتحديثات Streams القادمة من قاعدة البيانات عبر Riverpod `ref.watch()`.

---

### 4. معايير الأمان وخصوصية البيانات
- عدم تمرير أي مفتاح سري (API Key) في الشيفرة المصدرية أو في قاعدة البيانات العادية، بل يتم حفظه في `FlutterSecureStorage` المشفر بواسطة Android Keystore.
- عزل محرك الذكاء الاصطناعي بحيث لا يُرسل أي ملف أو نص للمحرك الخارجي إلا بعد موافقة يدوية وصريحة من المحامي.
- منع حفظ كلمات مرور النسخ الاحتياطي نصياً، واستخدام اشتقاق المفاتيح PBKDF2/Argon2.
